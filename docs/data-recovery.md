# 데이터 복구와 서비스 재개

## 기준과 범위

- 이 문서는 복구 목표, 검증 증거와 서비스 재개 조건의 기준입니다.
- 테이블의 삭제 의미와 복구 대상은 [테이블 설계](erd-design.md#삭제와-복구-경계)를 따릅니다.
- 파일의 식별과 제거 규칙은 [저장 객체 설계](erd-design.md#증거와-저장-객체)를 따릅니다.
- 작성 방식은 ASD-STE100의 명료성 원칙을 참고합니다. 한국어 문서의 정식 표준 준수를 뜻하지 않습니다.
- 현재 단계는 설계입니다. 백업 설정, 실제 복원과 서비스 재개를 수행하지 않았습니다.
- DB 백업은 기본 백업과 WAL 보관을 통한 PITR을 지원해야 합니다. 파일 백업은 아래 복구 목표를 충족해야 합니다. 도구·제공자의 선정과 설정은 후속 구현입니다. 승인되지 않은 운영 DB 작업을 실행하지 않습니다.

## 운영 결정

| 결정 항목 | 의미 | 확정 기준 |
|---|---|---|
| RPO | 장애 시 허용하는 데이터 손실 시간입니다. | 최대 15분 |
| RTO | 장애 발생부터 서비스 재개까지 허용하는 시간입니다. | 최대 4시간 |
| 콘텐츠 복구 기간 | 직접 삭제한 콘텐츠를 복구할 수 있는 기간입니다. | 삭제 시각부터 30일 |
| DB 백업 보존 기간 | 선택 가능한 복원 시점의 보존 기간입니다. | 최근 30일의 복원 시점을 유지 |
| 파일 보존 기간 | 현재 참조와 복구 가능한 참조의 파일을 보존하는 기간입니다. | 현재 참조, 콘텐츠 복구 기간과 보관 중인 DB 백업의 참조가 모두 종료될 때까지 보존 |
| 감사·이관·신고 증거 보존 기간 | 업무 이력과 증거를 보존하는 기간입니다. | 처리 종결 후 최소 180일; 유효한 참조·멱등성 처리에 필요한 이력은 해당 의존성이 종료될 때까지 보존 |
| 승인 책임자 | 대상, 복원 시점과 서비스 재개를 승인합니다. | 서비스 책임자 |
| 실행 책임자 | 복원과 검증을 수행합니다. | 백엔드 운영 책임자 |

2026-10-10 사용자 지시에 따라 초기 서비스 기준을 확정했습니다. 위 값은 제품의 복구 목표이며 달성한 측정값이 아닙니다. 파일과 DB의 보존 기간은 같은 복구 목표를 충족해야 합니다.

운영 수용 전에는 책임 역할을 실제 담당자와 연결하고 연락 경로를 기록합니다. 실제 복원으로 목표 달성을 증명하지 못하면 운영 수용을 완료하지 않습니다. 보존 기간의 법적 적합성은 별도 검토합니다. 기간 만료는 자동 삭제 승인이 아닙니다. 참조·멱등성·증거 보존 조건과 별도 삭제 승인 절차를 모두 확인합니다.

## 백업 범위

- DB 백업은 계정, 관계, 프로젝트와 커뮤니티를 같은 일관성 시점으로 보존합니다.
- PostgreSQL 스키마 분리는 독립 복구를 보장하지 않습니다. 모든 도메인에 사용자 참조가 있습니다.
- PostgreSQL 물리 PITR은 클러스터 전체를 복원합니다. 특정 테이블만 과거 상태로 덮어쓰는 기능이 아닙니다.
- 일부 콘텐츠 복구가 필요하면 먼저 격리 환경에 전체 백업을 복원합니다. 운영 병합 대상은 별도로 승인합니다.
- 백업은 검토된 마이그레이션과 보완 SQL의 버전을 추적합니다. Prisma 생성 SQL만 보관하지 않습니다.
- 파일 백업은 storage_code, object_key, sha256과 byte_size의 대응을 보존합니다.
- 원본 파일 보존 없이 사진 URL만 백업한 결과는 파일 복구 증거로 인정하지 않습니다.
- 백업 접근 권한은 복구 책임자에게 제한합니다. 백업에는 비밀번호 해시와 세션 정보가 포함됩니다.
- 백업 성공과 복원 성공을 구분합니다. 운영 수용 전에는 격리 환경에서 실제 복원을 수행합니다.

## 콘텐츠 복구

1. 승인 책임자는 삭제 작업 UUID와 대상 행 목록을 고정합니다.
2. 실행 책임자는 현재 데이터와 백업의 차이를 읽기 전용으로 확인합니다.
3. 실행 책임자는 현재 소유권, 부모 상태와 파일 존재를 확인합니다.
4. 실행 책임자는 고유 제약 충돌과 복구 기간 만료를 확인합니다.
5. 승인 책임자는 정확한 대상과 예상 변경을 승인합니다.
6. 복구 작업은 설계의 잠금 순서로 대상 행을 잠급니다.
7. 복구 작업은 삭제 작업 UUID와 현재 상태를 다시 검증합니다.
8. 복구 작업은 승인한 부모부터 같은 트랜잭션에서 복구합니다.
9. 실행 책임자는 노출 범위와 제외 대상의 상태를 검증합니다.
10. 실행 책임자는 승인 대상, 처리 주체, 처리 시각과 결과를 기록합니다.

- 상태가 승인 시점과 다르면 작업을 중단합니다. 변경된 대상을 자동으로 다시 승인하지 않습니다.
- 부분 실패는 DB 트랜잭션 전체를 롤백합니다. 외부 파일 복구를 같은 트랜잭션으로 간주하지 않습니다.
- 기존 내용이 변경됐으면 백업 값으로 자동 덮어쓰지 않습니다. 별도 병합 결정을 받습니다.
- 부모 복구 전후에 개별 삭제된 댓글의 숨김 상태를 확인합니다.
- 콘텐츠 복구 전후에 친구, 차단, 좋아요, 참여 기간과 세션 상태가 자동 변경되지 않았는지 확인합니다.

## 재해 복구

1. 승인 책임자는 장애 범위와 목표 복원 시점을 고정합니다.
2. 실행 책임자는 서비스 쓰기를 차단합니다.
3. 실행 책임자는 현재 DB와 로그의 보존 가능한 사본을 확보합니다.
4. 실행 책임자는 백업을 격리 환경에 복원합니다.
5. 실행 책임자는 원본 파일을 복원합니다.
6. 실행 책임자는 DB 관계와 파일 무결성을 검증합니다.
7. 실행 책임자는 복원 시점 이후의 탈퇴와 차단 변경을 대조합니다.
8. 실행 책임자는 기존 갱신 세션을 모두 무효화합니다.
9. 실행 책임자는 복원 전 발급한 접근 토큰의 사용을 차단합니다.
10. 실행 책임자는 캐시와 집계 결과를 무효화합니다.
11. 승인 책임자는 검증 증거를 검토합니다.
12. 승인 책임자는 서비스 재개를 별도로 승인합니다.

- 세션 행의 폐기만으로 접근 토큰 차단이 완료됐다고 가정하지 않습니다. 토큰 검증 방식에 맞는 무효화 수단을 구현해야 합니다.
- 탈퇴와 차단 변경은 운영 DB 복원으로 되돌아가지 않는 별도 변경 기록에 보존합니다. 기록에는 변경 식별자, 계정·관계 식별자, 처리 시각과 변경 상태를 저장합니다. 기록의 보존 기간은 감사 이력 기준을 따릅니다. 구체적인 저장소와 기록 전달 수단은 구현 단계에서 선정하고 전달 실패를 검증합니다.
- 대조 근거가 없으면 관련 계정과 접근 경로를 차단합니다. 영향 계정을 식별할 수 없으면 서비스 재개를 보류합니다.
- 과거 세션, 참여 권한과 차단 상태의 부활을 복구 성공으로 인정하지 않습니다.
- 격리 복원 결과를 운영에 반영하는 행위와 서비스 재개는 별도 승인 대상입니다.

## 검증 증거

| 확인 대상 | 필요한 증거 |
|---|---|
| 복원 시점 | 백업 식별자, 목표 시각과 적용한 마이그레이션 버전 |
| DB 기본 제약 | PK·UNIQUE·NOT NULL·CHECK·부분 고유 인덱스의 실제 존재와 실패 사례 |
| 논리 관계 | 고아 참조, 삭제 대상 참조와 잘못된 소유 관계의 검사 결과 |
| 프로젝트 권한 | 방장의 유효한 참여, 중복 참여 부재와 종료한 참여의 접근 거부 결과 |
| 이관 | 작업 공간 귀속, 변경 번호와 원 작성자·댓글·반응 식별자 보존 결과 |
| 콘텐츠 복구 | 개별 삭제된 자식의 숨김 유지와 고유값 충돌 거부 결과 |
| 파일 | 객체 키별 존재 확인, SHA-256 일치와 바이트 수 일치 결과 |
| 인증 | 과거 갱신 토큰과 접근 토큰의 거부 결과 |
| 탈퇴·차단 | 복원 이후 변경의 대조 기록과 불확실한 접근의 차단 결과 |
| 복구 목표 | 측정한 손실 시간, 복구 시간과 승인한 RPO·RTO의 비교 |

정적 스키마 검사와 문서 생성은 위 증거를 대신하지 않습니다. 테스트용 고정 데이터의 통과도 운영 백업 복원 증거를 대신하지 않습니다.

기술 근거: [PostgreSQL PITR과 전체 클러스터 복원](https://www.postgresql.org/docs/current/continuous-archiving.html), [ASD-STE100 작성 원칙](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf).
