# 복구와 파일 수명주기 실행 경계

## 권한과 승인

- 일반 사용자의 콘텐츠 권한과 운영 복구 권한을 구분한다.
- 서버는 `KNITTINGLOG_MAINTENANCE_APPROVER_USER_IDS`와 `KNITTINGLOG_MAINTENANCE_EXECUTOR_USER_IDS`에서 허용한 계정을 확인한다. 각 값은 쉼표로 구분한 UUID 목록이다.
- 설정이 없거나 UUID가 잘못되거나 중복되면 서버는 작업을 거부한다.
- 승인자와 지정 실행자는 서로 다른 활성 계정이어야 한다. 실행 시 현재 권한을 다시 확인한다.
- 승인과 실행은 `command_receipts`에 기록한다. 같은 실행 UUID와 같은 입력의 재시도는 중복 변경을 만들지 않는다.
- 승인 UUID를 다른 실행 UUID에서 다시 사용하지 않는다. 상태가 바뀌거나 승인이 만료되면 새 검토와 승인이 필요하다.

## 콘텐츠 복구와 역이관

모든 경로는 `/api/v1`을 접두어로 사용한다.

| 작업 | 경로 | 절차 |
|---|---|---|
| 콘텐츠 복구 | `POST /admin/maintenance/recovery/prepare`, `/approvals`, `/execute` | 승인자는 삭제 작업 UUID와 명시한 대상을 검토한다. 승인 요청에 `expected_snapshots`를 넣는다. 지정 실행자는 승인 UUID로 실행한다. |
| 역이관 | `POST /admin/maintenance/recovery/reverse-transfers/prepare`, `/approvals`, `/execute` | 승인자는 원 이관 UUID를 검토한다. 승인 요청에 `expected_snapshot`을 넣는다. 지정 실행자는 승인 UUID로 실행한다. |
| 콘텐츠 물리삭제 | `POST /admin/maintenance/content-purge/prepare`, `/approvals`, `/execute` | 승인자는 30일이 지난 직접 삭제 대상과 서버 보존 근거를 검토한다. 승인 요청에 `expected_snapshots`를 넣는다. 지정 실행자는 승인 UUID로 실행한다. |

- 콘텐츠 복구는 30일 이내의 직접 삭제 대상만 처리한다. 부모의 복구가 개별 삭제된 자식을 자동으로 복구하지 않는다.
- 복구 대상 종류는 프로젝트, 작업 공간, 카운터, 기록, 기록 댓글, 게시글과 게시글 댓글이다.
- 서버는 삭제 작업 UUID, 현재 소유자, 부모, 현재 참여와 변경 상태를 확인한다. 계정, 인증, 친구, 차단, 종료한 참여와 이관 이력을 되살리지 않는다.
- 복구는 같은 행의 식별자를 유지한다. 작업 공간과 카운터의 변경 번호를 갱신한다. 부분 실패는 전체 DB 변경과 실행 영수증을 롤백한다.
- 역이관은 원 이관 결과와 현재 작업 공간의 프로젝트와 변경 번호가 같아야 한다. 서버는 현재 참여 상한, 방장, 차단, 중복 작업 공간과 개인 프로젝트의 다른 참여자를 확인한다.
- 역이관은 새 참여 기간과 새 이관 이력을 만든다. 기존 이력과 개인 콘텐츠의 식별자는 변경하지 않는다. 떠나는 개인 프로젝트는 종료한다.
- 물리삭제는 현재 참조뿐 아니라 삭제된 자식과 보존 중인 관계·타이머·이력도 확인한다. 관련 행을 연쇄 삭제하지 않는다. 관계나 이력이 남은 프로젝트와 작업 공간은 삭제를 거부할 수 있다.
- 물리삭제의 서버 보존 인벤토리는 정확한 대상과 삭제 작업을 증명해야 한다. 구현체가 없거나 증거가 오래되거나 보존 기간이 남으면 삭제를 거부한다. 요청자가 전달한 보존 해제값은 근거가 아니다.

## 파일 처리

- `POST /storage/objects`는 `data_base64` JSON을 받는다. 최대 원본 크기는 10 MiB이다.
- `GET /storage/objects/:id`는 현재 소유자에게 검증한 Base64 바이트와 크기를 반환한다. 다른 사용자는 공개 프로필의 파일 UUID만으로 바이트를 읽을 수 없다.
- 프로필 사진은 `PATCH /users/me`의 `profile_photo_object_id`로 연결하거나 `null`로 해제한다. 신규 연결은 현재 소유한 미삭제·미제거 객체만 허용한다.
- 큰 JSON 본문 제한은 파일 경로에만 적용한다. 다른 API의 기본 JSON 제한은 유지한다.
- 저장소는 신뢰한 `storage_code`로 선택한다. 같은 코드를 다른 어댑터에 재연결하지 않는다. 기본 저장소를 임의로 선택하지 않는다.
- 로컬 파일 어댑터는 명시한 절대 경로와 비공개 디렉터리를 사용한다. 객체 키를 재사용하거나 기존 바이트를 덮어쓰지 않는다. 읽을 때 SHA-256과 크기를 확인한다.
- 로컬 서버에서 파일 처리를 켜려면 `MODE=local`과 `KNITTINGLOG_LOCAL_STORAGE_CODE`, `KNITTINGLOG_LOCAL_STORAGE_ROOT`를 함께 지정한다. 루트는 절대 경로이다. 두 저장소 값이 모두 없으면 파일 처리를 켜지 않는다. 일부 값만 있거나 다른 모드이면 시작을 거부한다.
- 서버 전용 `restoreVerified`는 신뢰한 백업 바이트의 SHA-256과 크기를 확인한 뒤 누락된 원래 키에 복원한다. 기존 파일은 덮어쓰지 않는다. 일반 사용자에게 임의의 키를 쓰는 API를 제공하지 않는다.
- 호출자는 명시한 작업 UUID로 서버 전용 `restoreFromBackup`을 사용한다. 현재 유지보수 실행자와 미삭제·미제거 객체를 확인한 뒤 불변 실행 의도를 기록한다. 외부 복원은 DB 트랜잭션 밖에서 수행한다. 완료가 확인되지 않은 복원이 있으면 제거 준비를 거부한다.
- 성공한 같은 작업은 중복 복원하지 않는다. 실패가 확정된 복원은 새 UUID로 재검토한다. 논리삭제 후에는 복원을 거부한다. 실행 중이거나 중단된 작업을 같은 UUID로 다시 시작하지 않는다.
- 프로세스 중단이나 완료 기록 실패로 남은 복원 의도는 시간 만료만으로 해제하지 않는다. 원 실행의 종료와 실제 바이트를 확인하는 운영 조정이 필요하다. 이 운영 조정 도구와 실제 백업 공급자는 이번 범위에 포함하지 않는다.
- 제거 준비는 `POST /storage/objects/:id/purge/prepare`에서 수행한다. 실행은 같은 객체의 `/purge/execute`에서 수행한다.
- 준비 단계는 현재 계정·프로젝트 참조, 삭제된 프로젝트의 복구 기간과 서버 백업 보존 근거를 검사한 뒤 객체를 논리삭제한다. 이후 새 참조를 차단한다.
- 외부 파일 제거는 DB 트랜잭션과 분리한다. 실제 제거에 실패하면 `purged_at`을 기록하지 않는다. 제거 뒤 DB 기록이 실패한 경우에는 같은 명령으로 재시도한다.
- 외부 제거 전에는 요청 UUID의 실행 의도 영수증을 확정한다. 같은 UUID의 다른 명령과 같은 승인의 다른 실행을 거부한다. 완료 결과는 서버가 유도한 UUID의 별도 불변 영수증에 기록한다.
- 실제 저장소와 실제 백업 인벤토리 연결은 별도 인프라 작업이다. 기본 보존 인벤토리는 미확인 상태를 반환한다. 이 상태에서는 영구 제거를 허용하지 않는다.
- 로컬 바이트 검사는 실제 운영 백업 복원, 재해 복구, RPO 또는 RTO 달성의 증거가 아니다.

## 분산 인증 제한

- 서버는 PostgreSQL의 `auth_attempt_limits`에서 로그인, 계정 복구와 복구 코드 재발급의 시도 수를 공유한다.
- 제한은 식별자별 10분 동안 10회이다. 로그인 성공 여부와 관계없이 시도를 센다. 11회부터 429를 반환한다.
- 창의 시각과 증가는 DB에서 처리한다. 실패한 인증 트랜잭션이 시도 수를 되돌리지 않는다.
- 식별자 원문, 비밀번호와 복구 코드는 제한 테이블에 저장하지 않는다. 제한 키는 해시이다.
- DB 장애나 감사 주체 폐기 시에는 503으로 거부한다. 프로세스 메모리로 우회하지 않는다.
- 만료 키 정리는 호출당 최대 100행으로 제한한다. 이 구현은 전역 잠금의 처리량이나 실제 다중 서버의 부하 수용을 증명하지 않는다.

## 인프라와 운영

- 향후 IaC는 Pulumi와 TypeScript를 사용한다. 이번 구현은 인프라 리소스를 만들지 않는다.
- 운영 DDL, 운영 환경 설정, 실제 백업 복원, 배포와 서비스 재개는 별도 대상 확인과 승인이 필요하다.
- 구현 검증 결과는 [보완 기록](implementation-validation.md)에 기록한다. 남은 작업은 [구현 현황](implementation-status.md)에서 추적한다.
